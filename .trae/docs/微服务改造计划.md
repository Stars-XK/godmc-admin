# 微服务改造计划

## 架构愿景
将现有的单体应用改造成基于 **Monorepo（单体仓库）** 模式的微服务架构。整体架构包含四个核心部分：
- **一个前端 (Frontend)**：独立的 Web 客户端应用，负责用户交互和界面展示。
- **一个主后端 (API Gateway)**：负责接收前端的 HTTP 请求、统一鉴权、参数校验、并将请求路由分发给底层的各个微服务。
- **众多其他微服务 (Microservices)**：纯业务逻辑处理单元（如 Auth、System、Monitor、Tools 等），通过 TCP/Redis/gRPC 等内部传输协议与主后端通信。
- **公共基础库 (Libs)**：存放数据库配置、Redis 缓存、工具类、常量、公共 DTO 等。

## 详细实施步骤

### 阶段一：Monorepo 工作区初始化 (Workspace Setup)
**目标**：将当前标准 NestJS 项目结构转换为 Monorepo 结构。
1. **更新配置**：修改 `nest-cli.json`，启用 `monorepo` 模式。
2. **目录重构**：
   - 创建 `apps` 目录（存放主后端和所有微服务）。
   - 创建 `libs` 目录（存放共享库）。
3. **主后端迁移**：将现有的 `src` 目录整体平移到 `apps/api-gateway/src` 中，作为初始的主后端（API 网关）。

*注：实体类、工具等内容将在后续阶段移动到顶层公共库。*

### 阶段二：抽取公共依赖层 (Extract Shared Libs)
**目标**：解决微服务之间的代码复用问题，避免重复代码。
1. **创建公共库**：在 `libs` 目录下创建 `common` 等公共库。
2. **代码迁移**：
   - 将原 `src/config` (配置文件) 移入公共库。
   - 将原 `src/utils` (工具类) 移入公共库。
   - 将原 `src/common` (拦截器、过滤器、装饰器、DTO基类) 移入公共库。
   - 将原 `src/shared` (数据库连接、Redis连接、日志服务) 移入公共库。
   - 将原所有实体类 (entities) 移入公共库，供各微服务共享。
3. **更新引用路径**：全局替换 import 路径，将相对路径或 `src/` 替换为 `@app/common/...` 等别名路径。

### 阶段三：搭建微服务底层通信机制 (Microservices Communication)
**目标**：让主后端具备调用底层微服务的能力。
1. **安装依赖**：安装 `@nestjs/microservices` 及所需传输层依赖。
2. **配置传输层**：初步采用 `TCP` 或 `Redis` 作为微服务间的通信机制。
3. **网关层配置**：在 `api-gateway` 中注册微服务客户端（ClientsModule），实现基于消息（Message Pattern）或事件（Event Pattern）的调用。

### 阶段四：剥离 Auth 微服务 (Extract Auth Service)
**目标**：将鉴权、登录、Token签发等核心安全逻辑独立。
1. **创建微服务**：生成 `apps/micro-auth`。
2. **逻辑迁移**：将原 `module/system/auth` 下的所有业务代码移入 `micro-auth`。
3. **网关层改造**：`api-gateway` 的 `AuthController` 仅作为 HTTP 接口层，内部通过 `@Client()` 调用 `micro-auth` 的具体实现。

### 阶段五：剥离 System 核心业务微服务 (Extract System Service)
**目标**：将用户、角色、菜单、部门等系统管理逻辑独立。
1. **创建微服务**：生成 `apps/micro-system`。
2. **逻辑迁移**：迁移原 `module/system` 下的所有业务代码（除 auth 外）。
3. **网关层改造**：主后端保留 Controller 对外暴露 RESTful API，业务逻辑下放给 `micro-system`。

### 阶段六：剥离 Monitor 微服务 (Extract Monitor Service)
**目标**：将监控相关逻辑独立。
1. **创建微服务**：生成 `apps/micro-monitor`。
2. **逻辑迁移**：迁移原 `module/monitor` 下的所有业务代码。
3. **网关层改造**：主后端保留 Controller 对外暴露 RESTful API，业务逻辑下放给 `micro-monitor`。

### 阶段七：剥离其他微服务 (Upload, Tools)
**目标**：彻底解耦所有业务模块，形成真正的“众多微服务”架构。
1. 创建 `apps/micro-upload` 处理文件上传业务。
2. 创建 `apps/micro-tools` 处理代码生成等工具类服务。

### 阶段八：前端整合与基础设施更新 (Frontend & DevOps)
1. **前端联调**：确保主后端（API Gateway）接口兼容原有前端逻辑。
2. **环境变量**：整理 `.env` 文件，为不同的微服务分配不同的端口。
3. **Docker 改造**：重写 `Dockerfile` 和 `docker-compose.yml`，支持一键拉起前端、主后端、及所有微服务容器。
4. **最终测试**：全链路联调测试。

*注：实体类、工具等内容已移动到顶层公共库，微服务通过引用公共库来使用这些资源。*
