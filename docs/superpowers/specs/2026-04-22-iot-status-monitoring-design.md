# 测点/设备/站点三态在线状态监控设计

## 业务需求
在复杂的物联网场景下，准确判断海量测点、设备及站点的在线/离线状态。支持三态模型（正常在线、部分离线/数据异常、完全离线）。超时判定需具备高度灵活性：全局默认 < 设备继承 < 测点独立。采用基于 Redis 的增量回写架构，保证实时状态计算性能与数据库状态的一致性。

## 核心架构设计

### 1. 预期周期配置体系 (Expected Cycle)
为满足“全局兜底、设备继承、测点覆盖”的灵活要求，引入如下字段：
- **`water_device` 表**: `expected_cycle` (INT, 默认 NULL, 单位:分钟)。表示该设备下所有测点的数据上报超时时间宽容度。
- **`water_point` 表**: `expected_cycle` (INT, 默认 NULL, 单位:分钟)。表示该具体测点的超时时间，配置时优先级最高。
- **全局配置**: 当测点和所属设备均未配置周期时，采用全局默认周期（如 15 分钟）。

### 2. 状态判定模型 (Three-State Model)
状态字段 `status` 复用现有的 0/1 体系，扩展为三态（建议值）：
- **`'0'` (正常在线/全在线)**: 所有启用状态的下级节点正常上报数据。
- **`'1'` (部分异常/数据异常)**: 下级节点中部分在线，部分超时离线。
- **`'2'` (完全离线/全离线)**: 下级所有启用状态的节点均超时离线。

**向上推导规则**:
- **测点 (Point)**: 根据当前时间减去最后活跃时间，对比 `expected_cycle` 决定是在线(0)还是离线(2)。
- **设备 (Device)**: 汇总其下属所有启用测点的状态。全0则为0，全2则为2，其余情况为1。
- **站点 (Station)**: 汇总其下属所有启用设备的状态。全0则为0，全2则为2，其余情况为1。

### 3. 数据流与存储 (Redis 增量回写)

**数据接入层 (`micro-data-integration`)**:
1. 当收到一条数据时，立刻更新 Redis 中该测点的**最后活跃时间** (Hash 结构: `iot:point:active` -> field: `pointCode`, value: `timestamp`)。

**状态监控层 (`micro-monitor` - Cron 定时任务)**:
1. **全量缓存构建**: 服务启动或定时（如每小时）将 MySQL 中设备、测点的层级关系及 `expected_cycle` 配置加载到内存或 Redis。
2. **高频心跳扫描 (如每分钟)**:
   - 从 Redis 读取所有测点的最新活跃时间。
   - 结合测点的 `expected_cycle`，计算出每个测点的当前状态 (0 或 2)。
   - 根据测点状态向上推导出设备状态 (0/1/2)。
   - 根据设备状态向上推导出站点状态 (0/1/2)。
3. **状态对比与增量回写**:
   - 将新计算出的状态树与上一次的状态树（缓存在 Redis `iot:status:tree`）进行比对。
   - 筛选出**状态发生变化**的节点（测点/设备/站点）。
   - 对于发生变化的节点：
     - 更新 Redis 中的当前状态树缓存。
     - 发送消息队列（或 TCP 调用）至 `micro-water-basic` 服务，执行 MySQL 的 `UPDATE` 操作持久化状态。
     - (可选) 记录设备上下线告警日志。

## 组件划分与服务边界
- **`micro-data-integration`**: 纯粹的数据接收器。责任最轻，只需向 Redis 写入 `pointCode` 对应的时间戳。
- **`micro-monitor`**: 状态大脑。负责定时扫库拉取层级关系、高频比对 Redis 时间戳、执行聚合逻辑、识别增量变化。
- **`micro-water-basic`**: 资产管理者。接收 `micro-monitor` 传来的状态变更指令，执行最终的 MySQL UPDATE。

## 数据结构示例
- **Redis Key `iot:point:active` (Hash)**
  - `point_A`: `1713000000000`
  - `point_B`: `1713000050000`
- **Redis Key `iot:status:tree` (String/JSON)**
  - 用于记录上一分钟推导出的各节点状态字典，如 `{"p_A": 0, "d_1": 1, "s_1": 0}`。
