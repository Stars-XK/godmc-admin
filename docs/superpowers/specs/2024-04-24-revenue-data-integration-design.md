# 营收数据接入与产销差报表设计方案

## 1. 背景与目标
本项目旨在为水务 DMA 系统提供可靠的营收数据接入、历史数据清洗、数据缺失自动回溯以及产销差（日报/月报）的自动计算功能。
系统需要面对 50 万以上的用户规模、千万级别的历史数据，以及复杂的数据场景（仅有日数据、仅有月数据、日和月都有、换表、插值等）。

## 2. 架构设计与存储模型
遵循 **MySQL + TDengine 混合存储** 原则：
- **MySQL**: 存储基础结构，包括：用户档案（户号、姓名、地址等）、分区结构（Zone）、用户与分区的绑定关系（zone_user_bind）、系统配置（参数字典）、数据接入任务配置。
- **TDengine (TSDB)**: 统一存储所有时序相关数据：
  - `revenue_meters_1d` (日营收用量，tag 包含 `user_code`, `zone_code`)
  - `revenue_meters_1mo` (月营收用量)
  - `zone_revenue_1d` / `zone_revenue_1mo` (基于底层用户向上聚合的分区总售水量)
  - 保留之前的 `zone_meters_1d` (供水量) 供产销差计算。

## 3. 核心问题与解决方案

### 3.1 参数配置模块完善
在“系统管理 -> 参数配置”中增加两大类：
- **DMA 系统配置**: 
  - `zone.night.flow.time` (夜间最小流量时间段，如 02:00-04:00)
  - `revenue.calc.strategy` (营收计算方式：`day_to_month`日算月、`month_to_day`月算日、`independent`独立计算)
- **GIS 地图配置**:
  - `gis.map.source` (地图来源：baidu / amap / tianditu / custom)
  - `gis.coord.transform` (坐标转换：WGS84_to_GCJ02, BD09_to_GCJ02, custom_proj4)
  - `gis.custom.proj4` (例如: `+proj=tmerc +lat_0=0 +lon_0=117...`)

### 3.2 历史数据处理与海量数据 (千万级)
- 采用 **系统内跑批任务** 处理。
- 在“接入任务管理”中允许配置时间范围（如 2014-01-01 至 2024-01-01）。
- 后端采用**时间切片 (Time Slicing) + 分页 (Pagination)**，将大任务拆分为无数小 Task，交由消息队列（如 Redis Queue / BullMQ）异步并发拉取源库，并在内存中批处理写入 TDengine，避免 OOM。
- 新增分区时，触发一个特定 `zone_code` 的“历史数据回溯任务”，从建表时间补齐。

### 3.3 数据缺失与突然断线 (自动回溯补全)
- 定时任务 (Cron) 每天/每小时执行正常接入。
- **缺失检测引擎**: 每日凌晨运行一次，扫描 TDengine 中的数据连续性。一旦发现某个用户在预期周期内无数据，将生成一条“补全任务”推入队列。
- **自动重试**: Worker 消费补全任务，主动发起请求去源库查询缺失的时间段。如果源库也无数据，根据系统配置进入“插值”流程。

### 3.4 复杂场景计算：换表与插值 (底层自动平滑)
- **换表处理**: 如果发现同一用户同一时间段内有两块表的度数（旧表最后读数与新表起度），底层自动相加：`当期用量 = (旧表最后读数 - 旧表上期读数) + (新表当前读数 - 新表起度)`。
- **插值 (月算日)**: 如果 `revenue.calc.strategy` 配置为 `month_to_day`，但某月用了 30 吨水。底层在清洗入库时，自动将 30 吨平滑均分（如 1吨/天）写入 `revenue_meters_1d`。
- 因为系统**只接入不填写**，所有的换表逻辑和插值算法都在 Node.js / Python 接入微服务层完成，最终向 TDengine 写入的都是“干净的、已平滑的日/月用量”。

### 3.5 报表与产销差计算 (日报/月报)
产销差 = 供水量 - 售水量
- **供水量 (设备端)**: 直接通过分区公式（如 A进 - B出）计算得出，已存于 TDengine 的 `zone_meters_1d`。
- **售水量 (营收端)**: 
  - **核心原则**: 售水量**仅统计最底层分区**（挂载了用户的最小网格），然后自底向上（Bottom-Up）逐级累加。
  - **计算流程**:
    1. 每天凌晨，计算最底层分区的所有用户用量之和（`SUM(val)` from `revenue_meters_1d` group by `zone_code`）。
    2. 将底层分区结果写入 `zone_revenue_1d`。
    3. 递归查询父分区，父分区的售水量 = $\sum$ 所有子分区的售水量。
    4. 联合 `zone_meters_1d` 与 `zone_revenue_1d` 生成最终的产销差日报表。

## 4. 后续开发计划建议 (Implementation Plan)
1. **阶段一**：完善参数配置页面及后端字典表（支持 DMA 配置和 GIS 坐标转换配置）。
2. **阶段二**：设计 MySQL 用户关联表与 TDengine 营收超级表结构。
3. **阶段三**：开发数据接入微服务（含定时任务、分片历史跑批、自动回溯补全引擎）。
4. **阶段四**：实现底层的平滑插值与换表算法。
5. **阶段五**：开发日报/月报的自底向上聚合算法及前端报表展示页面。
